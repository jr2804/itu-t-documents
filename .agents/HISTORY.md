## Format

| 2026-11-26 | The document identifiers mirror the ITU-T DMS: `T25-SG12-261015-TD-GEN-0520` for a temporary document, `T25-SG12-C-0192` for a contribution | The identifiers are the only stable address of a document in the DMS. Contributions, collective letters and reports are numbered across the study period, so their identifier carries no meeting | Initial commit |
| 2026-11-26 | The ITU-T login is a four step SAML handshake, not a form post | `auth.itu.int` hands a `SAMLRequest` to the identity provider at `login.itu.int`, which answers with a `SAMLResponse` for the assertion consumer service of `www.itu.int`. The credential post to `login.itu.int/my.policy` is the step in between | Initial commit |
| 2026-11-26 | The listing page size is set with the `ITUDMS_PageSize` cookie | The page size is a cookie, not a URL parameter; without it a listing is silently truncated at 50 rows | Initial commit |
| 2026-11-26 | The meeting document pages are decoded as ISO-8859-1 | Those pages do not declare a charset but are encoded in ISO-8859-1, while the `net4` pages are UTF-8 | Initial commit |
| 2026-11-26 | Study groups are zero padded to two digits, so study group 5 becomes `SG05` in the identifiers and in the paths | The ITU-T writes `T25-SG05-C-0538` and serves the study group pages under `/studygroups/2025-2028/05/`; the unpadded `T25-SG5` answers with an empty page. Only the `net4` applications take the plain number as `Group=5` | 2026-11-27 |
| 2026-11-26 | The metadata store keeps the meeting of a contribution even though the identifier carries none | The listing a contribution appears in is the only source of its meeting | Initial commit |
| 2026-11-27 | secretspec is an optional credential source below the environment and the configuration file | It lets users keep the TIES password in a real secret manager instead of a file, but the package must keep working without it: `secretspec_credentials` reads `ITU_TIES_USERNAME`/`ITU_TIES_PASSWORD` from the provider alias `itu-ties` and returns `None` on a missing extra, a missing manifest or an unresolvable provider, so the layer contributes nothing in the default install | Uncommitted |
| 2026-11-27 | The temporary documents of a meeting are read per sub-type | The aggregate listing of a meeting shows only a preview of five documents per sub-type, whatever the page size is: the meeting `T25-SG13-250303` has 549 temporary documents but the aggregate listing holds 30 rows. The listing of a single sub-type holds all of them, so the aggregate page is read for its sub-type links and every sub-type listing is read after it | Uncommitted |
| 2026-11-27 | A revision of a document is marked `!R1!` instead of `!!` | The DMS publishes the revisions of a document in place of the original separator, e.g. `T25-SG02-C-0001!R1!MSW-E.docx`. A revision may exist in more languages than the original, and the original may be withdrawn, so the parser keeps the revision number and the download prefers the original | Uncommitted |
| 2026-11-27 | The file name extension is taken from the download URL, not from the format | A document is published in the format it was submitted in: `T25-SG13-R-0001` is published as `!!MSW-E.doc` and not as a `.docx` file, while the other reports of SG13 are `.docx` files | Uncommitted |
| 2026-11-27 | The numbers of the documents are not consecutive | A withdrawn document leaves a hole, e.g. `T25-SG13-C-0669` does not exist between `C-0668` and `C-0670`. A number therefore does not prove that a document exists, and a status code does not prove it either — the access policy answers with a redirect before it validates the path | Uncommitted |
| 2026-11-27 | A listing that holds fewer documents than it reports is refused | The listing pages report their size (`Results: 82`), so a truncation by the page size can be detected instead of losing documents silently. `IncompleteListingError` is raised by `fetch_documents` and reported by the `sync` command | Uncommitted |
| 2026-11-27 | Every page of a listing is read | The page size control of the ITU-T web interface stops at 900, and the contributions of a study period exceed it: `T25-SG13` has 972, `T25-SG15` 1211, `T17-SG15` 2858. Reading one page made `fetch_documents` without a meeting end in `IncompleteListingError`. The `sync` command and the MCP tools list one meeting at a time, and no listing of a single meeting has more than 452 documents, so they were not affected yet. The pages link to the next one (`Next`, the row offset in `PageLB`), which `fetch_documents` follows for every kind of listing; the completeness check then counts the documents of all pages. A next link that leads back to a page that was read, or to a page without a new document, ends the reading, so a defective link cannot loop forever | Uncommitted |
| 2026-11-27 | The study groups, the working groups and the questions are read from the ITU-T, never hard coded | They change from period to period: SG9 and SG16 existed in 2022-2024 and were replaced by SG21 in 2025-2028. The catalogue reads the index page of a period and the structure page of a study group, and refuses an entity that does not exist | Uncommitted |
| 2026-11-27 | The study periods are a closed registry | The ITU-T publishes a fixed set of study periods, so a period that does not exist must not be constructible. `StudyPeriod.from_year(2025)` builds the period from a single year; `StudyPeriod.parse` also takes `"2025"` | Uncommitted |
| 2026-11-27 | The period code of a document identifier is looked up in the registry | The periods do not all span four years: `2022-2024` has three. A formula that adds three years to the code built `2022-2025`, which the registry refused, so no document of that period could be parsed. `DocumentRef.parse` now asks `StudyPeriod.parse("T22")` | Uncommitted |
| 2026-11-27 | The commands default to the current study period, `documents` to every period | A label written in the code goes stale at the next period, so the default is `StudyPeriod.current()`. The metadata store may hold documents of several periods, so `documents` searches all of them until a period is given; `--study-period` is applied by the CLI and by the MCP tools alike: `search_documents` dropped it, and `documents_for_question` and `contributions_by_source` let it scope only the synchronisation that runs before them while they searched the whole store; the three take `study_period` from the API methods as well | Uncommitted |
| 2026-11-27 | An empty study period option counts as not given | An environment variable that is set but empty — `ITU_T_DOCUMENTS_STUDY_PERIOD=` in a shell or a CI matrix — reached `StudyPeriod.parse("")` and crashed every command with a `ValueError`. An empty string now takes the default of the command | Uncommitted |
| 2026-11-27 | A detail page adds to what the listing told; it never replaces it | The detail page of a document names its title and its renditions and knows nothing of the posting date, the meeting, the sources or the questions. Storing it as a whole blanked all of them whenever a document was downloaded or its detail was read, so `store_detail` adds the renditions and keeps the rest | Uncommitted |
| 2026-11-27 | A stored document is returned once, whatever matched | A document can be submitted by several organisations whose names share a word. Joining the sources to filter by `source` returned the document once per matching source, and the duplicates used up the `limit`; the filter now selects the matching documents with a sub-query | Uncommitted |
| 2026-11-27 | The metadata store releases its connections when it is closed | `MetadataStore` opens an engine and nothing disposed of it, so every store left an unclosed SQLite connection behind — 26 in the test suite. `MetadataStore.close()` disposes the engine, and `ItuDocuments.close()` calls it for the store it opened | Uncommitted |
| 2026-11-27 | The MCP server is a package of small modules, one per group of questions | One module of 492 lines held a server, eleven tools and five helpers. A tool module per group of questions and `server.py` as the composition root, which lists every tool, keep each below 130 lines; the limit is a rule of `.agents/POLICIES.md`. The tool contract — names, descriptions, parameters and output schemas — was recorded before and after the move and did not change | Uncommitted |
| 2026-11-27 | An MCP tool is always equivalent to the CLI and the API, and the three change together | A capability that exists in one interface only is a gap in the others. The table of counterparts in `src/itu_t_documents/mcp/AGENTS.md` is read by `tests/test_mcp_server.py`, so a tool without an API method or without a command fails the suite unless it is a listed gap (`top_sources`) | Uncommitted |
| 2026-11-27 | Only the `mcp` command loads the MCP server | Every start of the command line imported the MCP libraries first: `--version` took 6–10 s. The command loads the package by name when it runs, which brings the start to about 3.3 s; a test pins that nothing else in the package imports it | Uncommitted |
| 2026-11-27 | A document outside the membership of the account is an `AccessDeniedError`, not a login failure | A TIES account is valid for the whole ITU-T, but its membership covers only the study groups it belongs to. Such a document answers 401 with a page that blames invalid credentials, which is not what happened; the login itself succeeds | Uncommitted |
| 2026-11-27 | The manifest of the secretspec provider is resolved by the package | secretspec only ever looks for a file named `secretspec.toml` in the current directory and its parents — it knows no `~/.config/secretspec/` and no `~/.secretspec.toml`, and `~/.config/secretspec/config.toml` holds secretspec's own configuration rather than a manifest. The package therefore resolves the manifest from `ITU_SECRETSPEC_MANIFEST`, the configuration file, the `secretspec.toml` of the configuration directory and the discovery of secretspec, in that order, and a manifest that cannot be read yields no credentials instead of an error | Uncommitted |
| 2026-11-27 | The version scheme is CalVer `YYYY.MM.N`, and the git tag is its only source | The year and the month say when the release happened and order the versions; the counter counts the releases of the month and starts again at `1` with every month. A plain date would forbid a second release on the same day, and a counter per year says nothing about the date. The version is resolved by `uv-dynamic-versioning` from the tag, so it is never written into `pyproject.toml`, and every state that is not an exact tag resolves to a PEP 440 development version that must never reach a package index | Uncommitted |
| 2026-11-27 | The tag keeps the zero of the month, the published version drops it | PEP 440 does not allow a leading zero in the release segment, so the version `2027.01.1` is published as `2027.1.1`. The tag is the spelling a human reads, the published version is the spelling the ecosystem accepts. The build backend drops the zero, so the artifact name, the metadata and the release on PyPI carry the same version, and the workflow computes the published version from the tag instead of comparing the tag with the artifact names | Uncommitted |
| 2026-11-27 | The publish job of the release workflow runs without a GitHub environment | The pending publisher on PyPI has an empty environment field, and PyPI compares the environment of the upload job with the environment of the publisher. A workflow that runs in the environment `pypi` would not match it, so the job must not name an environment at all | Uncommitted |
| 2026-11-27 | The actions of the workflows are pinned to references that exist | `astral-sh/setup-uv` publishes no major tag after `v7` and `pypa/gh-action-pypi-publish` has no tag `v1` — its moving reference is the branch `release/v1`. A reference that does not resolve fails the workflow before its first step, which is why the continuous integration was red on every push. setup-uv is pinned to the commit of its release, as its own documentation recommends, and the publisher to the branch `release/v1` | Uncommitted |
| 2026-11-27 | Every push to `main` is released: the workflow tags the commit with the next CalVer version | A release per push keeps the version on PyPI in step with the branch and takes the tagging out of the hands of the maintainer. The tag is pushed with the token of the workflow, and GitHub does not run a workflow for a push that its own token made, so the release of the automatic tag is the run that created it. A commit that carries a tag already is skipped, because a tag that was pushed by hand has its own release. The version is computed by `.github/scripts/calver.py`, which counts the releases of the month and never returns a version that is lower than the greatest one of the repository | Uncommitted |
| 2026-11-27 | The release publishes one universal wheel, tested on 3.13, 3.14 and 3.14t | The package is pure Python, so the wheel is `py3-none-any` and valid for every supported interpreter; cibuildwheel refuses to build a pure Python wheel at all. The support for the free-threaded build is proven by installing the built wheel and running the suite against it on all three interpreters | Uncommitted |
| 2026-11-27 | The documentation builder lives outside the project environment | It is a tool, not a dependency of the package, and the other tools of the project (ruff, ty, rumdl, codespell) are mise tools as well. `mise docs` runs it through `uvx` with a pinned interpreter and the plugins it needs — mkdocstrings renders the API reference, markdown-exec the examples, markdown-callouts the callouts. The builder reads the source statically and never imports the package, so the runtime dependencies are not needed. As a side effect the free-threaded job of the CI can install the test tools without the extra | Uncommitted |
